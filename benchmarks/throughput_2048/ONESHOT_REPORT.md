# 상주 프로세스 없는 단발 runner 검증

**앞선 제안은 조건을 보완해야 한다. 작업 등록 후 단발 실행 한 번만으로는
동시 작업의 완료를 보장하지 못했다.** 기존 상위 AI 작업이 맡긴 작업들의
완료 확인과 재실행까지 책임지는 경우에는 상주 daemon 없이 처리할 수 있다.
사용자가 runner를 관리하게 하거나 새 감시 서비스를 추가한 것은 아니다.

## 실제 CLI로 확인한 결과

mergetrain 3.0.6을 독립된 로컬 Git 저장소와 bare 원격에서 실행했다.
간단한 A/B 파일 변경과 제한 시간 있는 gate로 실행 순서를 고정했다.
이는 2048 기능 구현이나 속도 실험의 반복이 아니라 runner 생명주기 검증이다.
제품 코드나 큐 DB를 직접 수정하지 않았다. Python으로 DB를 읽은 것은
관찰·검증뿐이다. 사전 승인된 로컬 테스트 작업만 `--auto`로 등록했다.

| 조건 | 결과 |
|---|---|
| A 등록·단발 실행 후 B 등록·단발 실행 | 둘 다 배포 |
| A 처리 중 B 등록·두 번째 단발 실행 | 두 번째 실행은 exit 0, 이후 B는 queued로 남음 |
| 위 상태를 상위 작업이 확인하고 한 번 더 실행 | B도 정상 배포 |
| gate에서 첫 runner를 강제 종료, 이후 명시적으로 재실행 | 배포 전 중단된 A를 복구해 배포 |
| 사전 승인 없는 작업에 기본 단발 실행 | 배포하지 않고 queued 유지 |
| 같은 수동 작업에 validate-only 단발 실행 | validated까지만 진행, 원격 변경 없음 |

첫 실행과 승인 경계 검사를 추가한 두 번째 독립 실행에서 동시성 대기 사례가
동일하게 재현됐다. 모두 예상 결과를 검증하는 assertion을 통과했다.
강제 종료는 테스트가 소유한 프로세스 그룹 하나에만 적용했고, 실행 프로세스는
finally에서 정리했다. 수동 승인 경계 fixture의 validated 작업은 의도적으로
로컬 원격에 배포하지 않았다.

## 놓치면 안 되는 실행 순서

1. runner A가 작업 A를 가져가 gate를 실행한다.
2. 다른 작업 B가 큐에 등록되고 runner B를 실행한다.
3. runner B는 아래 메시지를 내고 exit 0으로 종료한다.

```text
mergetrain daemon tick: runner is active; leaving its in-progress train untouched
```

4. runner A는 처음 가져간 A만 배포하고 종료한다.
5. 두 프로세스가 모두 종료했지만 B는 여전히 queued다. 원격에도 B가 없다.

즉 큐 데이터가 삭제되거나 중복 배포된 것은 아니다. **처리를 이어갈 실행
주체가 없어진다.** 종료 성공 코드나 현재 실행 하나의 성공만으로 사용자
요청 전체가 완료됐다고 판단하면 안 된다.

기존 `daemon --once`는 한 batch를 처리하는 명령이다. 새로 들어오는 작업까지
모두 비울 때까지 실행하는 명령으로 구현된 것이 아니다. `daemon.py:153-166`의
활성 runner 확인, `:216`의 claim, `:373`의 once 종료 조건과 실제 결과가 일치한다.
Luna MAX의 독립적인 읽기 전용 검토에서도 같은 한계를 확인했다.

## 상주 daemon 없이 사용할 수 있는 현재 절차

기존 상위 AI 작업이 이미 담당하는 유한한 작업 묶음을 기준으로 한다.

1. 하위 에이전트는 구현·커밋·등록을 마치고 결과를 상위 작업에 반환한다.
2. 상위 작업 하나가 승인된 범위에서 단발 runner 실행을 담당한다.
3. 실행이 끝나면 **자신이 맡긴 작업들의 결과**를 확인한다. 다른 runner가
   실행 중이면 완료를 기다리고, 대상 작업이 남으면 다시 실행한다.
4. 충돌·실패는 소유 에이전트가 수정하고 retry한다. 반환된 replacement 작업까지
   추적하고, 원래 작업이 canceled됐다는 이유만으로 성공으로 세지 않는다.
5. 요청한 작업의 배포·검증 완료가 확인된 뒤 상위 작업도 종료한다.

테스트에서는 이 재확인 단계가 남아 있던 B를 실제로 처리했다. 따라서
짧게 살아 있는 기존 AI 작업이 이 책임을 갖는 절차는 가능하다. 다만 완성된
자동 기동·이벤트 전달 기능을 새로 구현하거나 배포한 것은 아니다.

상위 AI 실행까지 중단되면 새 실행이 필요하다. 이번 배포 전 강제 종료
검사에서도 재실행 후 복구는 됐지만, 종료된 프로세스가 스스로 다시 시작된
것은 아니다. 상주 주체 없이 어떤 중단에서도 무조건 자동 재개된다는
제품 계약은 현재 근거로 약속할 수 없다.

## 적용 범위와 다음 판단

- 검증한 중단 시점은 **push 전에 gate가 실행 중인 상태**다. push 중·직후의
  모호한 원격 상태를 실제로 주입한 실험은 아니다. 정적 검토상 그런 경우는
  기존 reconcile 경로를 따르며, 자동 재실행만으로 해결한다고 일반화하지 않는다.
- 강제로 순서를 제어한 두 실행은 문제 재현을 위한 증거다. 모든 경쟁 조건을
  검증했다거나 종료 직전의 모든 가능한 순서를 탐색했다는 뜻은 아니다.
- 새로운 CLI·설정·감시 프로세스는 추가하지 않았다. 원본 저장소의 기존
  대기 작업과 공개 배포도 실행하지 않았다.

추천은 **각 하위 에이전트가 runner를 제각각 실행하게 하는 방식 대신,
현재 상위 AI 작업에 완료 확인 책임을 두는 것**이다. 이 방식으로 지침을
구체화할 수 있지만, 단순한 enqueue→once만을 자동 완료 계약으로 제품화하면
안 된다. 작업 등록만으로 완전한 자동 완료를 제공하려면 실행 종료와 새 작업
등록 사이의 인계를 별도로 설계해야 한다. 그 비용을 검토하기 전에는
새 자동 기동 기능을 추가하는 것이 더 단순하다고 단정하지 않는다.
