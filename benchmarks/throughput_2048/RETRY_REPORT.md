# 기존 retry로 무개입 완료가 가능한가 — 재검증

**이 사례에서는 가능했다. 새 복구 기능이 필요하다는 가설은 지지되지 않았다.
그러나 retry를 사용해도 일반 Git보다 빨리 끝나지는 않았다.**
잘못된 안내를 고치는 것과 전체 완료 시간을 줄이는 것은 별개의 과제다.

## 무엇을 바꿔 확인했나

앞선 실험은 일반 Git을 Luna가, mergetrain 명령을 부모가 담당해 운영 방식이
달랐다. 이번에는 각 방식에 새 GPT-5.6 Luna MAX 한 개를 배정했다. 각각
충돌 수정·명령 실행·검사·로컬 배포까지 담당했고 부모는 중간 조언이나
코드 수정을 하지 않았다. 마지막에 결과를 별도로 검증했다.

두 저장소 모두 동일한 시작 커밋 `c32408153dbf0ca6f7f483b7e91fff6b18c9e0f0`,
동일한 원본 병렬 패치 네 개, 동일한 순서와 동결된 합격 기준을 사용했다.
구현을 다시 시키거나 기존 충돌 해결 코드를 복사하지 않았다.
mergetrain은 수정 후 기존 `retry`를 사용하도록 처음부터 알려줬다.
따라서 **기능을 아는 운영자의 완료 가능성**을 확인한 것이며, 처음 접한
에이전트가 retry를 스스로 발견하는지 시험한 것은 아니다.

범위는 2048 게임 로직 네 기능의 통합이다. 각 시도 제한은 10분이었다.
원격은 `/private/tmp/mt-luna-retry-check-20260905/{manual,train}.git`뿐이며,
공개 배포·제품 코드 수정·DB 직접 편집·`--auto`는 수행하지 않았다.
수동 deploy 계획 확인은 해당 Luna가 로컬 목적지를 확인하고 처리했다.

## 결과

| 항목 | 일반 Git / Luna MAX | mergetrain 3.0.6 / Luna MAX |
|---|---:|---:|
| 통합 커밋의 전체 검사 통과 | 3분 1초 | 6분 27초 |
| 로컬 push와 배포 후 검증 완료 | 3분 15초¹ | 6분 52초² |
| 부모가 추가로 해결해 준 횟수 | 0 | 0 |
| 사용자에게 질문·승인을 요청한 횟수 | 0 | 0 |
| 실제 로컬 push 횟수 | 1 | 2 |
| 기록된 명령 수 | 20 | 47 |

¹ 일반 Git은 전체 검사를 통과한 동일 HEAD를 push한 뒤 baseline 검사를
완료한 시점이다. 이후 원격 SHA 확인도 수행했다.
² mergetrain의 deploy 내장 verify 완료 시점이다. 재조립되어 배포된 실제
SHA를 별도 checkout에서 다시 전체 검사한 시점은 **7분 22초**였다.
둘 다 최종 원격 SHA와 깨끗한 checkout, 전체 6개 검사 그룹을 부모가 확인했다.

시작은 각 spawn 직전 기록한 시각이다. 기록과 실제 모델 작업 시작 사이의
분리되지 않은 준비·스케줄링 시간이 포함된다. 한 번의 비교이며 모델의
명령 선택·실수·처리 속도 차이도 있어 성능 배수나 retry의 인과적 시간
효과를 추정할 수 없다. 이전 실험과 시계 시작 기준도 달라 개선율을
계산하지 않았다. 원시 시각·계산은 [retry-results.json](retry-results.json)에 있다.

## retry가 실제로 한 일

1. 첫 validate에서 moves가 충돌하고 나머지 세 작업은 validated가 됐다.
2. Luna가 moves 소유 worktree에서 undo를 병합하고 충돌을 수정·검사·커밋했다.
3. `retry 2 --json` 한 번이 **0.185초**에 성공했다. 작업 2를 `canceled`로
   남기고 수정 SHA `30ce0f6a9f18f8bce4d87f0f70b8ba2259e42d4f`를 작업 5로
   등록했다. 별도의 dismiss, enqueue, 제거된 옵션 사용은 없었다.
4. 재검증은 `validated_train_pending`으로 막혔다. retry는 이미 준비된
   세 작업의 묶음을 대체하거나 함께 재검증하는 동작까지 수행하지 않는다.
5. Luna가 기존 세 작업을 로컬 배포하고, 작업 5를 검증·전체 검사·배포했다.
   두 번의 `y` 입력도 Luna가 처리했다. 사용자 개입으로 세지 않았다.
6. 최종 상태는 healthy/idle이었다. 네 기능은 deployed, 원래 충돌 작업
   하나는 canceled로 증거가 남았다. `done:5`는 다섯 기능 성공이 아니다.

이 흐름에서 retry 자체의 오동작은 재현되지 않았다. 앞선 실험의 중복 등록
오류와 제거 옵션 실패를 피할 수 있다는 것은 확인했다. 부분 배포를 먼저
하는 절차는 남았다. 다른 기존 recovery 경로로 이를 피할 수 있는지나,
daemon·사전 승인 모드의 성능은 이번에 검증하지 않았다.

## 남아 있는 시간의 해석

기록된 명령 실행 시간의 합은 일반 Git 0.78초, mergetrain 34.82초다.
후자는 interactive deploy 두 명령의 28.44초를 포함하며, 그 안에는 Luna가
로그를 읽고 확인 입력을 보내는 대기도 있다. 일부 명령은 동시에 실행됐고
모든 읽기·편집·모델 처리를 계측한 것도 아니므로 이것을 벽시계 시간의
정확한 분해나 순수 엔진 비용으로 해석하면 안 된다.

47개 명령이 제품의 필수 최소 명령 수라는 뜻도 아니다. 상태·inspect·
원격 조회·별도 최종 검증과 에이전트 실수가 포함된다. 보존한 실수는 다음과 같다.
추가로 버전·도움말 출력 5개는 별도 로그로 보존했으며 시간 기록이 없어
위 명령 수·실행 시간 합에 포함하지 않았다.

- 지원하지 않는 `integration`을 개별 검사 그룹으로 지정했다가 올바른
  `baseline,undo,moves`로 수정했다. 제품이나 게임 코드 결함이 아니다.
- 아직 로컬에만 있는 검증 후보 SHA를 bare 원격에서 조회해 `bad object`가
  났다. 이어서 로컬 후보 worktree를 만들어 검증했고 부모 도움은 없었다.

두 실수도 관찰 시간에서 빼지 않았다. 이 결과는 단순한 retry 노출만으로
전체 완료 시간이 줄어든다고 주장할 근거를 주지 않는다. 다만 실제 검사
계산보다 모델이 상태를 해석하고 도구를 오가는 과정이 큰 개선 후보임을
다시 보여준다. 비용·토큰 사용량은 제공되지 않아 계산하지 않았다.

## 이번 확인으로 결정할 수 있는 것

- **새 복구 기능부터 만들지 않는다.** 기존 retry로 이 사례를 끝낼 수 있었다.
- **확정된 안내 불일치는 고친다.** 제거된 옵션을 권하는 오류와
  수정 후 enqueue만 안내하는 지침을 기존 retry 경로와 맞추는 것이 우선이다.
- **속도 문제는 별도로 다룬다.** 부분 묶음과 수정 작업을 처리하면서
  반복되는 확인·재조립·배포 중 무엇을 기존 경로로 줄일 수 있는지 검토한다.
  새 명령·설정·스케줄러를 추가해야 한다는 결론은 아직 아니다.
- 다음 비교를 한다면 동일 담당자가 기존 경로에서 불필요한 조회와 명령
  왕복을 줄인 경우를 측정해야 한다. 줄인 뒤에도 남는 절차에만 제품 변경을
  검토한다. 작업 요청 전체 완료와 사용자 개입을 별개 지표로 유지한다.

무개입 완료는 이번에 양쪽 모두 달성했다. 따라서 이것만으로 mergetrain의
차별적 가치를 입증하지는 못했다. 현재 증거에 맞는 결론은 **복구 능력은
이미 있지만, 사용 경로의 안내와 조정 비용은 개선 여지가 있다**는 것이다.
