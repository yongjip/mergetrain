# 기존 daemon 경로 검증과 속도 개선 우선순위

**새 자동 실행 기능을 만들기 전에 기존 daemon 경로를 활용할 근거를 확보했다.**
사전 승인된 로컬 목적지에서 충돌 없는 작업은 검증과 배포가 이어졌고,
수정 작업의 retry도 승인 정보를 유지해 자동으로 처리됐다. 계속 실행 중인
daemon이 다음 주기에 재시도를 처리하는 것까지 별도 확인했다.

다만 전체 완료 시간이 기계적 실행 시간에 가까워진 것은 아니다. 이번 Luna
실행도 약 6분 24초가 걸렸다. 다음 개선 대상은 기존 경로를 명확히 안내하고
에이전트의 불필요한 확인과 명령 왕복을 줄이는 것이다.

## 두 가지 확인

주 실험은 새 GPT-5.6 Luna MAX 한 개가 기존과 동일한 원본 병렬 커밋 네 개를
통합하는 방식이었다. 제품 3.0.6과 합격 기준을 유지했다. 승인된 실험용
로컬 원격에만 `enqueue --auto`를 사용하고, `daemon --once`로 첫 묶음을
처리한 뒤 소유 브랜치에서 충돌을 수정·커밋·retry하고 다시 처리했다.
부모가 코드나 복구 절차를 대신 해결하지 않았다.

보조 실험은 새로운 격리 저장소에서 daemon을 계속 실행했다. 첫 부분 배포
이후 **이전에 검증된 수정 커밋을 재생**하고 retry했다. 모델의 충돌 수정
시간을 재측정한 것이 아니라, 추가 runner 호출 없이 다음 주기에 자동
처리되는지 확인한 기계적 실험이다. 기본 주기 15초를 변경하지 않았고,
전체 프로세스를 제한 시간 내 종료했다.

두 실험 모두 최종 로컬 원격의 실제 SHA를 깨끗한 checkout에서 확인했고
동일한 전체 6개 검사 그룹을 통과했다. 외부 배포나 제품 코드 변경은 없다.

## 확인된 절차 감소

| 동일한 네 기능 통합에서 관찰한 항목 | 이전 수동 retry 경로 | 이번 daemon 경로 |
|---|---:|---:|
| baseline gate 실행 | 4회 | 2회 |
| 배포 후 verify | 2회 | 2회 |
| 로컬 push | 2회 | 2회 |
| 에이전트의 interactive 배포 확인 입력 | 2회 | 0회 |

검증하고 나서 별도로 deploy해 재조립하는 왕복이 줄었다. 첫 daemon 명령은
1.356초에 세 작업을 배포하고 하나를 blocked로 남겼다. 수정 후 두 번째
명령은 0.885초에 나머지 작업을 배포했다. 합계 2.242초는 해당 runner 명령의
실행 시간이며 전체 작업 시간이 아니다. 두 번의 부분/최종 push는 그대로다.

retry 결과에는 이전 작업과 새 작업 모두 `auto_deploy: true`가 기록됐다.
이번 동일 목적지·정책에서 승인 유지가 동작했다는 증거다. 다른 목적지나
정책으로 승인이 이전된다고 해석해서는 안 된다. 수동 경로에서 발생했던
`validated_train_pending` 왕복과 확인 입력은 이번 경로에서 필요하지 않았다.

## 시간 분해와 한계

| 주 실험의 관찰 구간 | 시간 |
|---|---:|
| spawn 직전 기록 → 실제 배포 SHA의 전체 검사 통과 | 383.856초, 약 6분 24초 |
| 그 구간 안에 기록된 명령 실행 구간의 합집합 | 7.588초 |
| 기록된 명령 구간 밖의 미분류 시간 | 376.268초 |
| 시작 기록 → 첫 계측 명령 시작 | 85.265초 |

동시 명령을 중복 합산하지 않도록 구간의 합집합을 계산했다. 미분류 시간에는
모델 판단, 초기 준비·스케줄링, 도구 왕복, 계측하지 않은 읽기·편집, 계측
wrapper의 부가 시간이 섞여 있다. 따라서 **376초를 순수 모델 추론이나 제거
가능한 낭비로 부르면 안 된다.** 사용자 승인 대기나 모델 추론만을 별도로
재는 수단은 이번에 없었다. interactive 확인이 없었다는 사실과 자동 승인
검토 서비스의 처리 시간이 0이라는 주장은 서로 다르다.

끝난 뒤의 추가 상태 확인까지 포함해 계측 명령은 68개, 시간 합은 8.646초다.
이전 실험과 읽기 계측 범위가 달라 68 대 47을 필수 명령 수의 증감으로
비교하지 않았다. 같은 이유로 이전의 7분 22초와 이번의 6분 24초 차이를
확정적인 개선율로 제시하지 않는다. 모델·prompt·승인 모드와 실행 조건이
다른 각 1회의 관찰이다.

보조 실험에서는 retry 반환 후 최종 배포 관찰까지 **15.407초**, daemon 시작
부터 실제 SHA의 전체 검증까지 **17.227초**였다. 기본 15초 주기의 영향이
드러났다. 첫 묶음의 처리와 검사 시간, 0.1초 간격 관찰 오차도 포함된다.
이 수치는 사전 계산된 수정 커밋을 사용하므로 AI 통합 시간과 비교할 수 없다.
같은 daemon 프로세스 하나가 재시도를 처리했고 SIGTERM 이후 exit 0으로 종료했다.

run_events도 보존했지만 타임스탬프가 초 단위라 0.08초 수준의 gate를 정밀
분해하는 근거로 사용하지 않았다. API 토큰·계정 비용은 제공되지 않았다.

## 에이전트가 추가로 한 일도 보존했다

Luna는 숨겨진 `--auto`를 확인하려고 probe 작업을 실제 등록한 뒤 취소했다.
이 때문에 첫 실작업은 id 2, 충돌 작업은 id 3, replacement는 id 6이 됐다.
probe와 실패 이력을 지우거나 시간을 제외하지 않았다. 이미 사용법을 제공한
상태에서도 탐색 비용이 발생했지만, 이 탐색이 제품의 필수 단계는 아니다.

지원하지 않는 개별 `integration` 검사 그룹 호출은 실패했고 이후 올바른
검사를 수행했다. `rg`의 exit 1은 충돌 표식이 없다는 정상 검사 결과였다.
프로세스 조회는 샌드박스에서 실패한 뒤 외부 조회로 확인했다. 이들을 모두
게임이나 daemon의 결함으로 분류하지 않았다.

Luna의 최종 응답 턴은 사용량 한도로 실패했지만, 그 전에 배포·합격·깨끗한
상태를 입증하는 로그가 완성돼 있었다. 부모가 실제 원격 SHA를 다시 검증했다.
보조 스크립트 생성도 자동 승인 검토 서비스의 한도 오류로 처음 거절됐다.
사용자의 continue 이후 읽기 전용으로 로컬 격리를 확인하고 같은 생성 작업을
재시도해 승인받았다. 해당 중단 시간은 실행 전이므로 보조 실험 성능에 넣지 않았다.

## 추천하는 다음 변경

1. **사전 승인된 범위에서는 기존 daemon이 끝까지 담당하도록 안내한다.**
   목적지·정책 승인 → 완료 브랜치 등록 → 단일 daemon 처리 → 충돌 시 소유
   에이전트 수정·retry → 같은 daemon이 이어서 처리하는 경로다. 새로운
   복구 명령이나 스케줄러가 있어야 이 흐름이 가능한 것은 아니다.
2. **오류·작업 지침을 실제 경로와 일치시킨다.** 제거된 옵션을 권하는 안내를
   고치고, 수정 후에는 지원되는 retry를 사용하게 한다. 승인된 자동 경로의
   사용법과 경계를 명확히 해 probe·도움말 탐색을 줄일 수 있는지 확인한다.
3. **필요한 증거를 모아 주고 중복 조회를 줄인다.** 이번에 반복된 status,
   inspect, 원격 확인 중 무엇이 필수인지 검토한다. 정확한 SHA 확인과 최종
   합격 검사는 유지하면서 기존 출력과 에이전트 지침을 먼저 정리한다.
4. **15초 주기 조정은 그다음이다.** 실제 목표 지연에 문제가 되는 경우 기존
   interval 설정으로 비교할 수 있다. 분 단위 미분류 시간을 해결하는
   주된 수단은 아니며, 이번에는 값을 조정하지 않았다.

지금 단계에서 광범위한 외부 리서치나 검증 캐시·새 설정 추가가 우선이라는
근거는 없다. 먼저 기존 경로 안내와 불필요한 왕복을 줄인 후 같은 조건을
여러 번 재생해야 한다. 긴 빌드가 있는 프로젝트와 외부 사용자 환경에 대한
효과는 아직 별도로 검증해야 한다.
