# 2048 병렬 개발 파일럿 결과 — 2026-09-05

이번 실행에서는 병렬 구현의 작은 시간 이득이 통합 과정에서 사라졌다.
mergetrain 3.0.6은 충돌을 감지하고 최종 결과를 안전하게 로컬 원격에
통합했지만, 충돌 복구 안내의 실제 오류와 추가 절차도 재현됐다.
우선 개선할 대상은 검사 엔진의 속도보다 **복구 과정의 판단·명령 왕복**이다.
단일 관찰 실험이며 아래 시간 차이를 mergetrain의 인과적 성능 비용으로
해석해서는 안 된다.

| 구간 | 관찰 시간 | 종료 기준 |
|---|---:|---|
| Luna 한 개의 순차 구현 | 6분 4초 | 커밋 후 전체 검사 통과 |

| 일반 Git 통합만 | 약 2분 10초 | 충돌 수정·통합 커밋·전체 검사 통과 |

| 병렬 시작 → mergetrain 전체 검사 | 약 11분 34초 | 부모 진단·인계·복구 시간 포함 |

일반 Git의 로컬 push 후 baseline 검증까지는 통합 시작부터 약 2분 25초,
mergetrain의 실제 배포 SHA에 대한 외부 전체 검사까지는 약 5분 20초였다.
순차 구현은 로컬 원격 배포를 수행하지 않았으므로 이 두 배포 시간과 직접
비교하지 않는다. 위 전체 검사 비교에서도 통합 운영 방식이 비대칭이다.

**시간 정밀도의 한계:** 순차 dispatch는 시작 전에 기록했지만 병렬 시작은
세 spawn 호출 직후 기록한 대용 시각이다. 따라서 병렬 시간은 실제 dispatch
기준보다 조금 짧다. 일반 Git은 에이전트가 관찰한 시작 시각을 사용한다.
병렬 시작 전 대화 압축·진행 공백 4분 32초는 별도 기록했고 병렬 성능으로
귀속하지 않았다. 에이전트가 보고한 검사 시작을 구현 시작으로 오인하지
않았다. 특히 저장 기능은 검사 후 커밋했으므로 검사 시각으로 완료를
앞당겨 계산하지 않았다. 정확한 원시 시각과 계산은 [results.json](results.json)에 있다.
순차 결과를 부모가 확인한 시점은 6분 47초로 전체 검사보다 43초 늦었다.
병렬도 마지막 커밋과 부모 확인 사이에 약 38초가 있었다. 두 수신 지연을
기능 구현 완료 시간과 혼동하지 않는다.

## 실제로 시간이 쓰인 곳

개별 Node 검사 프로세스는 대체로 0.07–0.08초였다. 순차 에이전트의 기록된
검사 9회 합계도 0.69초다. 일반 Git 통합에서 기록한 merge·commit·검사·push
9개 명령의 합은 0.59초였다. 이는 읽기·편집 등 모든 도구 시간을 수집한
수치가 아니며, 나머지를 전부 모델 추론 시간이라고 부를 수 없다.

mergetrain 쪽의 기록된 32개 명령은 합계 18.88초였다. 여기에는 상태·도움말·
오류 재현·추가 진단도 있고, 두 interactive deploy 명령 13.34초에는 부모가
계획을 확인하고 `y`를 전달하는 대기가 포함된다. 순수 엔진 실행 시간이나
필수 사용자 작업 횟수로 해석할 수 없다. 사용자에게 추가 판단이나 승인을
요청하지 않았으며, 사용자의 인지 부담 감소 여부는 이번에 측정하지 못했다.

일반 Git의 독립 baseline 명령은 통합 결과의 push 전후 각 1회였다.
전체 검사 안의 baseline 그룹은 이 횟수에 포함하지 않았다. mergetrain은 validate와
deploy가 각각 재조립·검증하면서 baseline gate 4회와 배포 후 verify 2회를
실행했다. 이번처럼 검사가 짧으면 절약 가능한 계산 시간은 작다. 긴 CI를
가진 게임에서 같은 결론이 나오는지는 검증하지 않았다.

## 재현된 문제와 정상 동작의 구분

### 1. 확정된 안내 오류: 제거한 옵션을 복구 방법으로 권함

이동 횟수 작업이 충돌한 뒤 소유 브랜치에서 수정·커밋하고 다시 enqueue하면:

```text
branch 'codex/moves' already has an active job. ...
dismiss it first ... or re-enqueue with --allow-duplicate.
```

실제로 권장 옵션을 사용하면 exit 2로 실패했다:

```text
mergetrain: v3 removed enqueue option --allow-duplicate;
exact SHAs and readiness are always verified
```

`dismiss 2` 후 수정 브랜치를 enqueue하면 성공했다. 즉 복구 자체는 가능하지만
오류 메시지의 대안 하나가 실행 불가능하다. `src/mergetrain/persistence/jobs.py:77`,
`src/mergetrain/git_runner.py:782`, `src/mergetrain/git_runner.py:1342`에 같은
제거 옵션 안내가 남아 있다. 첫 경로는 실행으로 재현했고 나머지는 정적 확인이다.
저장소의 “수정·커밋 후 새 job enqueue” 지침에도 필요한 dismiss 단계가 빠져 있다.
기존 `retry <job-id>` 경로도 존재한다. 이번에는 안내에 따라 dismiss와 enqueue를
사용했으므로 retry의 시간·정확성은 평가하지 않았다. 이 경로를 포함해 기존
복구 안내를 정리하는 것이 새 동작 추가보다 먼저다.

### 2. 관찰된 절차 비용: 부분 검증 후 수정 작업을 바로 합치지 못함

첫 validate는 moves를 blocked로 남기고 undo·analysis·storage 세 작업만
validated로 만들었다. 수정 후 validate는 `validated_train_pending`으로
실패하면서 기존 묶음을 먼저 배포하도록 안내했다. 공개 기본 경로를 따라
세 작업을 로컬 배포한 후 수정 작업을 다시 검증·배포해 총 두 번 배포했다.

이는 이번 기본 경로의 동작이지 데이터 손상 버그라는 뜻은 아니다. 다만
“네 기능을 맡기고 완료 결과를 받기”라는 사용자의 목적에 비해 복구 단계가
많았다. 별도 내부 recovery 경로로 줄일 수 있는지는 이번에 비교하지 않았다.

### 3. 부분 검증 성공은 네 기능 완료가 아님

첫 부분 묶음은 baseline을 통과했지만 외부 전체 검사는
`moveCount starts at zero: undefined !== 0`으로 실패했다. 원래 부분 묶음에도
실행할 수 있도록 baseline만 gate로 정한 실험 조건이므로, 이를 mergetrain이
기능 버그를 놓쳤다는 증거로 삼지 않는다. `status`는 blocked 작업을 명확히
표시했다. 사용자 목표 단위의 완료 판정은 별도로 필요하다는 사례다.

### 4. 혼동 가능한 inspect 표현

blocked 작업을 inspect하면 같은 출력에 `phase: gating · success`와
`outcome: failure / merge_conflict`가 함께 나타났다. 배치 진행과 개별 작업
결과의 범위 차이로 보이며, 실제 성공으로 오판정했다고 단정하지 않는다.
에이전트가 상태를 해석할 때 불필요한 재확인을 유발할 수 있는 표현이다.

## 권장 순서

1. **기존 복구 계약부터 일치시킨다.** 제거된 옵션 안내를 고치고 문서·오류·
   structured next_action이 실제 실행 가능한 동일한 복구 경로를 가리키게 한다.
   실패 → 소유 브랜치 수정 → 완료까지의 왕복 수와 성공률로 확인한다.
2. **겹치는 변경의 작업 분할을 조정한다.** 이번 undo와 moves는 같은 상태와
   이동 코드를 바꿨다. 다음 비교에서는 이 둘을 한 에이전트가 순서대로 맡고,
   보드 분석·저장 검증을 병렬로 실행하는 세 작업 구성을 비교한다.
   새 스케줄러 기능을 만들 필요 없이 작업 배정만으로 검증할 수 있다.
3. **부분 완료 뒤 재통합 경로를 줄일 수 있는지 먼저 설계한다.** 기존 승인·
   정확한 SHA·복구 증거를 유지하면서 수정 작업까지 한 번에 마무리할 수
   있는지 검토한다. 새 명령이나 설정 추가 전에 기존 경로 통합을 우선한다.
4. 위 수정 후 같은 패치를 같은 운영 주체·prompt·완료 기준으로 여러 번
   교차 순서 재생한다. 충돌 없는 경우와 충돌 있는 경우를 나누고, 그 다음
   긴 검사가 있는 실제 게임 규모로 넓힌다. 총 완료 시간과 사용자 개입을
   각각 기록한다. 이번 한 번으로 평균·p95·비용 절감률을 추정하지 않는다.

이번 결과는 “mergetrain이 필요 없다” 또는 “병렬 개발은 느리다”를 입증하지
않는다. 이 작은 사례에서는 결정적인 Git·검사 계산보다 작업 분할과 복구
조정이 더 큰 개선 대상이었다는 근거를 제공한다. 실제 토큰·계정 비용은
native subagent 도구에서 제공되지 않아 저렴해졌다는 주장도 하지 않는다.
